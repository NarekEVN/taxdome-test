## 1. Problem summary

A firm (the **payer**) submits one HTTP request containing N payments to other firms (**payees**).

- If the payer's balance covers the **sum of all payments** → persist every payment, debit the payer by the total,
  credit each payee, return **201**.
- Otherwise → change nothing, return **422**. The request is all-or-nothing.

Hard constraints:

1. Service runs as **multiple load-balanced instances** → no in-process locks or caches can guarantee correctness;
   the database is the only coordination point.
2. **Relational DB** (we use PostgreSQL 16).
3. Language: Ruby / Python / Go → **Python 3.11** (the existing project is a PyCharm/Python 3.11 project).
4. Prefer commonly used libraries.

## 3. Data model

The assignment defines two tables. We keep their columns and add only constraints, indexes and one audit column.

```sql
-- db/001_schema.sql
CREATE TABLE firms (
    id            INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name          TEXT    NOT NULL,
    balance_cents BIGINT  NOT NULL CHECK (balance_cents >= 0),
    uuid          TEXT    NOT NULL UNIQUE
);

CREATE TABLE payments (
    id            INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payer_firm_id INTEGER NOT NULL REFERENCES firms(id),
    payee_firm_id INTEGER NOT NULL REFERENCES firms(id),
    amount_cents  BIGINT  NOT NULL CHECK (amount_cents > 0),
    description   TEXT    NOT NULL,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CHECK (payer_firm_id <> payee_firm_id)
);

CREATE INDEX payments_payer_firm_id_idx ON payments (payer_firm_id);
CREATE INDEX payments_payee_firm_id_idx ON payments (payee_firm_id);
```

```sql
-- db/002_seed.sql  (exactly the assignment's seed + identity bump)
INSERT INTO firms (id, name, balance_cents, uuid) VALUES
  (1, 'Pinecrest CPA Group', 5000000, '3f1c9a2e-7b4d-4c1e-9a55-2d8e6f0b7c41'),
  (2, 'Lopez Bookkeeping',     50000, '8b2e4c71-0d3a-4f6e-b1c9-5a7d2e9f4c10'),
  (3, 'Nair Tax Services',    200000, 'e5f18b3c-2a9d-4c07-8e6b-1d4a7f9c3b25');
SELECT setval(pg_get_serial_sequence('firms', 'id'), (SELECT max(id) FROM firms));
```

Deviations from the assignment schema (document in README):

- `balance_cents` / `amount_cents` are **BIGINT**, not INTEGER. A 32-bit int caps at ~$21.4M, which a large
  practice's balance or a bulk total can exceed.
- `CHECK (balance_cents >= 0)` — a DB-level safety net: even if application logic were wrong, an overdraft cannot commit.
- `CHECK (amount_cents > 0)`, `CHECK (payer <> payee)`, FKs, `UNIQUE (uuid)`, `created_at` — integrity/audit only.

Schema is applied by Postgres' `docker-entrypoint-initdb.d` on first start and by the test fixtures for the test DB.
(Alembic is the production-grade upgrade path — listed under improvements.)

## 4. API

### 4.1 `POST /bulk-payments`

Creates a bulk payment (a collection resource, so a plural noun with no verb, lowercase and hyphenated per REST URI
conventions). The payer stays in the body, so the payload is unchanged.

Request (`Content-Type: application/json`):

```json
{
  "payer_firm_uuid": "3f1c9a2e-7b4d-4c1e-9a55-2d8e6f0b7c41",
  "payments": [
    { "amount": "1200.75", "payee_firm_uuid": "8b2e4c71-0d3a-4f6e-b1c9-5a7d2e9f4c10", "description": "Bookkeeping cleanup, 3 clients" }
  ]
}
```

**201 Created**

```json
{
  "payer_firm_uuid": "3f1c9a2e-...",
  "total_amount_cents": 1325125,
  "payments": [
    { "id": 1, "payee_firm_uuid": "e5f1...", "amount_cents": 625000, "description": "Overflow returns, August 2026" }
  ]
}
```

Payments are returned in request order.

**422 Unprocessable Entity** — every client-side rejection, with a machine-readable code:

```json
{ "error": { "code": "insufficient_funds", "message": "Payer balance does not cover the total of 1325125 cents." } }
```

| `code`                 | When |
|------------------------|------|
| `validation_error`     | Malformed JSON, wrong types, missing/extra fields, bad amount format, bad UUID, empty `payments`, too many payments, bad description. `details` lists the offending fields. |
| `unknown_payer_firm`   | `payer_firm_uuid` not in `firms`. |
| `unknown_payee_firm`   | One or more `payee_firm_uuid` not in `firms`. `details` lists them. |
| `self_payment`         | A payment's payee equals the payer. |
| `insufficient_funds`   | Payer balance < sum of amounts. **The case the assignment requires.** |

Other statuses:

- `503 Service Unavailable` + `Retry-After: 1` — transaction still failing with a deadlock/serialization error after retries (see §6.4), or DB unreachable.
- `500` — unexpected bug (generic body, details only in logs).

Decision: one status (422) for all input problems, distinguished by `code`. Simpler for clients, matches FastAPI's
default for validation errors, and the assignment only mandates 422 for denial. (Alternative noted in README: 400 for
malformed JSON, 404 for unknown payer.)

### 4.2 Helper endpoints (verification only)

- `GET /health` → `200 {"status":"ok"}` after `SELECT 1`. Used by compose/nginx.
- `GET /firms/{uuid}` → `200 {"uuid","name","balance_cents"}` or `404`. Lets reviewers check balances without psql.
  (In production this would require auth; out of scope here.)

## 5. Validation rules

All validation happens **before** opening a DB transaction (cheap rejections never touch locks).

| Field | Rule |
|-------|------|
| body | JSON object; unknown keys rejected (`extra="forbid"`) |
| `payer_firm_uuid` | required; valid UUID string; normalized to lowercase canonical form before lookup |
| `payments` | required; array; `1 ≤ len ≤ 1000` (`MAX_PAYMENTS_PER_REQUEST`, configurable) |
| `payments[].amount` | required; **must be a JSON string** (numbers rejected — avoid float precision loss); regex `^\d{1,12}(\.\d{1,2})?$`; value `> 0` |
| `payments[].payee_firm_uuid` | required; valid UUID; normalized; must differ from payer |
| `payments[].description` | required string; stripped length `1..1000` |

Amount → cents conversion (`app/utils/money.py`), **no floats anywhere**:

```
"300"      -> 30000
"5800.5"   -> 580050
"1200.75"  -> 120075
"0.01"     -> 1
"0", "0.00"            -> reject (not positive)
"-5", "1.234", ".5", "5.", "1e3", " 5", "5,00", 5 (number) -> reject
```

Implementation: split on `.`, `int(whole) * 100 + int(frac.ljust(2, "0"))` (or `Decimal` with exact quantize). Max per
payment is 12 integer digits (< $1T) → totals of 1000 payments fit BIGINT easily.

Duplicate payees in one request are **allowed** (the sample request pays Nair twice). Each entry becomes its own
`payments` row; credits are aggregated per payee.

## 6. Core algorithm & concurrency (the important part)

### 6.1 Threats we must handle

| Race | Example | Consequence if ignored |
|------|---------|------------------------|
| Double-spend / overdraft | Two instances process two requests from Pinecrest at once; both read $50k, both pay $40k. | Negative balance / money created. |
| Lost update on credit | Lopez is credited by two payers concurrently via read-modify-write. | One credit vanishes. |
| Deadlock | A pays B while B pays A concurrently; each locks itself, then waits for the other. | Postgres aborts one txn (40P01) → spurious 5xx. |
| Partial write | Crash after debit, before credits. | Money disappears. |

### 6.2 Chosen approach: one DB transaction, pessimistic row locks in a global order

Inside **one transaction** (READ COMMITTED, Postgres default):

```sql
-- 1. Lock every involved firm row, always in ascending id order.
SELECT id, uuid, balance_cents
FROM firms
WHERE uuid IN (:uuid_1, ...)        -- payer + distinct payees
ORDER BY id
FOR UPDATE;
```

2. In Python: resolve payer and payees from the result.
   - payer missing → rollback, `unknown_payer_firm`
   - any payee missing → rollback, `unknown_payee_firm`
   - `payer.balance_cents < total` → rollback, `insufficient_funds`
3. Insert all payments in one multi-row statement, `RETURNING id`. Request order is guaranteed by SQLAlchemy's
   `sort_by_parameter_order=True` (Postgres alone doesn't promise RETURNING order for multi-row inserts).
4. `UPDATE firms SET balance_cents = balance_cents - :total WHERE id = :payer_id`
5. Credit payees with aggregated amounts, one statement:
   ```sql
   UPDATE firms f SET balance_cents = f.balance_cents + v.credit
   FROM (VALUES (:id1, :c1), (:id2, :c2)) AS v(id, credit)
   WHERE f.id = v.id;
   ```
6. `COMMIT` → 201.

Why this is correct across N instances:

- **Overdraft**: the payer row is locked `FOR UPDATE` before the balance is read. A concurrent request for the same
  payer blocks on step 1 until we commit, then reads the *new* balance. Check-then-act is atomic.
- **Lost updates**: all writes are relative (`balance = balance ± x`) on rows we hold locks on.
- **Deadlocks**: every transaction acquires firm locks in the same global order (ascending `id`) in a single
  statement, so no wait cycle can form. In Postgres the `LockRows` step runs above the `Sort`, so `ORDER BY id FOR UPDATE`
  locks in id order.
- **Atomicity**: single transaction → all-or-nothing; any exception → rollback.
- **Defense in depth**: `CHECK (balance_cents >= 0)` makes an overdraft impossible to commit even with a logic bug.

Lock scope is per-firm rows only, so unrelated firms never contend. Locks are held for a handful of statements
(milliseconds). Hot-payee contention (many payers crediting one big firm) is noted under improvements.

### 6.3 Alternatives considered (put in README)

| Option | Verdict |
|--------|---------|
| Conditional debit `UPDATE ... SET bal = bal - :t WHERE id=:p AND bal >= :t` + credits | Correct for overdraft and elegant, but credit-row locks are then taken in arbitrary order → deadlocks on cycles unless we still pre-lock in order. Pre-locking subsumes it. |
| `SERIALIZABLE` isolation + retry | Correct but higher abort rate under contention; harder to reason about; still needs retries. |
| Optimistic locking (version column) | Needs schema change and retry loops; more aborts on hot payers. |
| `pg_advisory_xact_lock(payer_id)` | Protects payer only; credits still need care. Row locks already do this. |
| App-level/Redis distributed lock | Extra infra, failure modes (lock expiry), and the DB still has to be right. Rejected. |

### 6.4 Retries

Wrap the transaction in a retry loop for transient errors only: SQLSTATE `40P01` (deadlock) and `40001`
(serialization failure). Max 3 attempts, small jittered backoff (e.g. 10–50 ms). Business rejections are never retried.
After exhaustion → 503. With ordered locking deadlocks should not happen; the retry is a safety net.

### 6.5 Request handling and idempotency

- The service does **not** auto-retry a request after a commit; a client retry after a timeout could double-pay.
  Proper fix is an `Idempotency-Key` header (optional stretch, §9).
- Request handler must not hold the transaction open while doing anything other than the statements above.

## 7. Code layout

One responsibility per package. Files marked *(later)* are created by the implementation step that needs them.

Layering rule: `routes` (HTTP) → `services` (business rules, transaction boundary, retries) → `repositories`
(SQL only, take an open connection, never commit) → DB.

- Routes parse with `schemas`, call one service function, and shape the response. No SQL, no business rules.
- Services know nothing about HTTP. They raise `DomainError`s that `api/error_handlers.py` maps to 422.
- Repositories hold every SQL statement, so the locking in §6.2 is in one place. They use the Core tables in
  `models/`; the SQL files in `db/` stay the source of truth for DDL.
- `core` and `utils` import nothing from the layers above them.

## 8. Testing strategy

All DB tests run against real Postgres (`payments_test` DB from compose). Each test truncates both tables
(`TRUNCATE payments, firms RESTART IDENTITY CASCADE`) and re-seeds.

| Level | File | What it proves |
|-------|------|----------------|
| Unit | `test_money.py` | Table-driven amount parsing incl. all reject cases in §5. |
| API/validation | `test_validation.py` | Each `validation_error` / `self_payment` / unknown-firm case → 422, DB unchanged. |
| API/happy path | `test_bulk_payments_api.py` | **Assignment sample**: 201, balances exactly 3674875 / 170075 / 1405050, 3 payment rows. Insufficient funds → 422 and nothing written. Exact-balance payment (total == balance) → 201, balance 0. |
| Concurrency | `test_concurrency.py` | See below. Uses a thread pool where each worker has its **own DB connection** (= separate instance). |

Concurrency tests:

1. **No overdraft**: payer balance $100; 20 parallel requests of $10 → exactly 10×201, 10×422, final balance 0,
   10 payment rows.
2. **No deadlock on cycles**: firms A and B each pay the other, 50 parallel requests mixed both directions → all 201,
   no 5xx, balances match expected arithmetic.
3. **Conservation of money**: random parallel bulk requests among seeded firms → `SUM(balance_cents)` unchanged,
   no negative balances, and for every firm `initial + credits − debits == final` computed from `payments`.

Use a `threading.Barrier` so requests actually start together. Keep runtime < 10 s.

Manual/e2e: `make demo` (sample request via curl through nginx) and `scripts/concurrency_demo.sh`.

## 9. Out of scope / improvements (for README)

- **Authentication/authorization**: in production the payer must come from the authenticated principal, never trusted
  from the body. Assumed handled by an upstream gateway.
- **Idempotency-Key** (stretch, if time allows): table `idempotency_keys(key TEXT, payer_firm_id INT, request_hash TEXT,
  response_status INT, response_body JSONB, created_at, PRIMARY KEY (payer_firm_id, key))`, inserted in the same
  transaction; replay returns the stored response; same key + different body → 422.
- Group rows of one request with a `bulk_payment_id` / batch table for audit and reporting.
- Double-entry ledger (immutable entries, balances derived/cached) instead of mutable balances.
- Hot-account contention: many payers crediting one firm serialize on its row; options are sharded sub-balances or
  async credit application.
- Alembic migrations, structured logging with request IDs, metrics (latency, 422 rate, retry count), rate limiting.
- Currency is USD-only, as specified.

## 10. Assumptions (for README)

1. All firm balances start non-negative; balances may never go negative.
2. Paying yourself is rejected.
3. Duplicate payees in one request are allowed and stored as separate rows.
4. Description is required, non-empty, ≤ 1000 chars.
5. Amount must be a JSON string; JSON numbers are rejected.
6. All input errors → 422 with a distinguishing `code`.
7. UUIDs are matched case-insensitively (normalized to lowercase; seeds are lowercase).
8. Max 1000 payments per request.
